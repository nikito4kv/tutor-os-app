# Спецификация — редизайн карточки ученика (A, V, H, L)

Фаза **S** (Specification) SPARC: фиксируем требования, краевые случаи, инварианты и
критерии приёмки. Псевдокод — в файлах `01_*`…`04_*` этой папки.

Основано на дизайн-разборе карточки (сессия SPARC Designer). Рекомендации, которые там были
помечены P0–P3, здесь получают устойчивые коды и спецификацию:

| Код   | Было | Суть                                                                     |
| ----- | ---- | ------------------------------------------------------------------------ |
| **A** | P0   | Зона «Требует внимания» — учебные to-do вверху обзора                    |
| **V** | P1   | Витальная полоса: баланс-герой + инлайн «Пополнить» при низком балансе   |
| **H** | P2   | Шапка: частотное действие наверх, «Редактировать» — в меню; CTA в пустых |
| **L** | P3   | Раскладка обзора в две колонки на `lg+`                                  |

## 0. Контекст и принципы

Карточка ученика — «центр всего» (`docs/PRODUCT.md`): профиль, баланс, уроки, заметки, ДЗ.
Сейчас она читается как **пассивная панель**: четыре статовые поверхности подряд, главное
действие в шапке — редкое «Редактировать», предупреждения (низкий баланс, нет урока) — тупики
без действия. Цель редизайна — превратить её в **рабочий кокпит**: «что мне сейчас сделать с
этим учеником» видно сразу, а каждое предупреждение ведёт к действию. Это **перекладка уже
существующих данных + проброс уже существующих диалогов** (`AddLesson`, `AddPackage`,
`EditStudentDialog`), без новых сущностей и без миграций.

Эталон зоны — `src/features/students` (правила проекта). Ленивая загрузка по `?tab=` (perf-срез
P3) и дешёвые head-COUNT для бейджей (`getStudentTabCounts`) — **сохраняем**, новый функционал
встраиваем в эту модель, а не ломаем её.

Правила проекта и `docs/DESIGN.md`: бизнес-логика и данные — в `queries.ts`/`actions.ts`,
не в компонентах; чистые агрегаты — отдельными функциями с юнит-тестами (как `overview.ts`);
UI-тексты только через `t.*` (`src/lib/i18n/ru.ts`), без хардкода строк; цвета — только токены
(`bg-success/10`, `text-warning`, …), без сырых hex; иконки — `lucide-react`, иконки-кнопки с
`aria-label`; состояния loading/empty/error; формы добавления — через `FormDialog`
(`docs/DESIGN.md` §7, ADR-0002); фокус виден на всех интерактивных элементах (`focusRing`);
проверка в светлой **и** тёмной теме; адаптив 375/768/1024/1440 без горизонтального скролла;
никакого `any`. Стек — Next 15 App Router, Supabase, Zod, vitest.

## 1. Глоссарий зон карточки (после редизайна)

| Зона                 | Где                   | Видна на        | Owns                                              |
| -------------------- | --------------------- | --------------- | ------------------------------------------------- |
| **Шапка**            | над балансом          | всех вкладках   | имя, предмет·уровень, primary-действие, «···»     |
| **Витальная полоса** | между шапкой и табами | всех вкладках   | баланс (герой) + инлайн «Пополнить» при низком    |
| **Табы**             | под полосой           | всех вкладках   | overview / packages / lessons / homework          |
| **Зона внимания**    | верх вкладки overview | только overview | учебные to-do: проверить ДЗ, просрочка, нет урока |
| Обзор-детали         | вкладка overview      | только overview | next-lesson, контакты, ссылка, активность         |

**Разделение ответственности (чтобы не дублировать):** деньги/баланс/пополнение живут в
**витальной полосе (V)** и НЕ повторяются в зоне внимания; учебные to-do живут в **зоне
внимания (A)** и не повторяются в полосе. Это ключевой инвариант композиции (INV-X1 ниже).

## 2. Сквозные инварианты

- **INV-X1.** Ни один сигнал не отрисовывается в двух зонах сразу: баланс — только V;
  «проверить ДЗ / просрочка / нет урока» — только A.
- **INV-X2.** Перекладка не меняет загрузку данных по вкладкам (матрица perf-P3 сохраняется):
  на non-overview вкладках не появляется новых запросов; единственная новая выборка — один
  head-COUNT просроченных ДЗ **только** на вкладке overview (см. A).
- **INV-X3.** Все новые поверхности проходят токены/тёмную тему/фокус/адаптив (чек-лист
  `docs/DESIGN.md` §12). Никаких сырых цветов.
- **INV-X4.** Миграции БД не требуются. Новых бизнес-констант не требуется
  (`LOW_BALANCE_THRESHOLD` уже есть).

## 3. A — зона «Требует внимания»

**Проблема.** Самое полезное (ДЗ ждут проверки, просроченная домашка, нет следующего урока)
сейчас выражено только мелкими бейджами-счётчиками на табах. Карточка не отвечает на вопрос
«что мне сделать прямо сейчас».

### Функциональные требования

- FR-A-1. Чистая функция `buildAttentionItems({ toReview, overdue, noUpcoming })` →
  упорядоченный массив элементов внимания. Без React/Supabase → юнит-тестируема (рядом с
  `buildActivityFeed` в `overview.ts`).
- FR-A-2. Порядок приоритета (фиксированный): `review` (кто-то ждёт тебя) → `overdue`
  (ученик просрочил) → `noUpcoming` (надо запланировать).
- FR-A-3. Входы зоны берутся из уже загруженного на overview:
  - `toReview` = `homeworkToReview` (проп, уже считается в `getStudentTabCounts`, статус
    `submitted`);
  - `overdue` = новый head-COUNT просроченной **невыполненной** домашки (`status = 'assigned'`
    **и** `due_at` не null **и** `due_at < now`) — см. FR-A-5;
  - `noUpcoming` = `overview.nextLesson == null` (нет ближайшего `scheduled`).
- FR-A-4. Действия по элементам (через `t.*`, без хардкода):
  - `review` → ссылка на `?tab=homework`, метка «Проверить»;
  - `overdue` → ссылка на `?tab=homework`, метка «Открыть»;
  - `noUpcoming` → диалог `AddLesson` (studentId + lessonsLeft), метка из `AddLesson`.
- FR-A-5. `getStudentOverview` дополняется полем `homeworkOverdue: number`, посчитанным
  **одним** head-COUNT (`count: "exact", head: true`) **только** на вкладке overview. Поле
  добавляется в интерфейс `StudentOverview`.
- FR-A-6. Рендер зоны — `Card` с заголовком `t.students.attention.title`, список строк
  (иконка + текст + `Badge` со счётчиком + действие). Рисуется **только если** `items.length
  > 0`. Если пусто — слим-строка `t.students.attention.allClear`(low-emphasis,`text-muted-foreground`), не карточка.
- FR-A-7. Зона размещается **первым блоком** контента вкладки overview (до KPI-плиток).

### Инварианты

- INV-A-1. `overdue` (просрочка) и `toReview` (на проверке) **не пересекаются**: `overdue`
  считает только `status = 'assigned'`, а `toReview` — только `submitted` → одна и та же ДЗ не
  попадает в обе строки (зеркалит INV-X1 на уровне данных).
- INV-A-2. Зона не показывает баланс/деньги (это зона V).

### Краевые случаи

- EC-A-1. Всё в норме (0/0/есть урок) → карточки нет, видна слим-строка «всё в порядке».
- EC-A-2. ДЗ `submitted` **и** просрочена по `due_at` → попадает в `review` (её надо
  проверить), не в `overdue` (т.к. `overdue` фильтрует `status='assigned'`). Двойного счёта нет.
- EC-A-3. ДЗ без `due_at` → в `overdue` не попадает никогда (FR-A-3, как `isHomeworkOverdue`).
- EC-A-4. `reviewed` просроченная → не считается (терминальна).
- EC-A-5. Время — наивно-локальное (как весь MVP, `date.ts`); сравнение по абсолютному времени.

### Критерии приёмки

- AC-A-1. На overview-вкладке ученика с непроверенной сданной ДЗ видна строка «ДЗ ждут
  проверки» с правильным счётчиком и кнопкой «Проверить» → ведёт на `?tab=homework`.
- AC-A-2. Ученик с просроченной невыполненной (`assigned`, `due_at` вчера) ДЗ → строка
  «Просроченная домашка» с счётчиком.
- AC-A-3. Ученик без `scheduled`-уроков в будущем → строка «Нет запланированных уроков» +
  открытие `AddLesson`.
- AC-A-4. Всё в норме → карточки внимания нет; видна слим-строка «всё в порядке».
- AC-A-5. Юнит-тесты `buildAttentionItems` покрывают порядок (FR-A-2) и пустоту (EC-A-1).
- AC-A-6. Открытие `?tab=lessons/packages/homework` НЕ выполняет COUNT просрочки (INV-X2) —
  он только в `getStudentOverview`.

Псевдокод: `01_attention-zone.md`.

## 4. V — витальная полоса (баланс-герой + инлайн «Пополнить»)

**Проблема.** Баланс — главное число продукта («сколько занятий осталось»), но визуально равен
«Оплачено». Бейдж «пора пополнить» — тупик: чтобы пополнить, надо уйти на вкладку «Пакеты».

### Функциональные требования

- FR-V-1. Текущая отдельная `Card` баланса (`page.tsx`, блок «Balance summary») заменяется
  **горизонтальной витальной полосой**: слева крупное число + подпись, при низком балансе —
  `Badge variant="warning"` (`t.students.lowBalance`); справа — инлайн-кнопка «Пополнить»,
  показанная **только** при `lowBalance`.
- FR-V-2. «Пополнить» открывает существующий `AddPackage` (studentId). Чтобы дать собственную
  метку/вид кнопки, `AddPackage` получает **опциональный** проп `trigger?: ReactNode` (зеркалит
  уже существующий паттерн `EditStudentDialog`); поведение по умолчанию (без `trigger`) не
  меняется.
- FR-V-3. Полоса видна на **всех** вкладках (как и текущая balance-card) и использует уже
  загруженные `lessonsLeft` + `lowBalance` (`page.tsx`) — новых запросов нет.
- FR-V-4. Низкий баланс подсвечивается токеном `warning` через мягкую заливку
  (`docs/DESIGN.md` §2: `bg-warning/10`/`text-warning` на тинте), здоровый — нейтрально.
  Сырых цветов нет.
- FR-V-5. KPI-плитки обзора (`student-overview.tsx`: next-lesson / to-review / paid) **не
  содержат баланс** (он теперь в полосе) — состав плиток не меняется этим пунктом (next-lesson
  правится в H, перенос в aside — в L).

### Инварианты

- INV-V-1. Баланс считается из того же `getStudentBalance` — формула не меняется.
- INV-V-2. Порог низкого баланса — `LOW_BALANCE_THRESHOLD` (TS-константа), не поле БД (как
  сейчас, perf-L2).

### Краевые случаи

- EC-V-1. Баланс выше порога → «Пополнить» не показывается, бейджа нет, полоса нейтральна.
- EC-V-2. Баланс 0 → бейдж + «Пополнить»; число `0` читается (контраст ≥4.5:1).
- EC-V-3. Очень длинное число занятий (теоретически) → полоса не ломает раскладку (gap-wrap).
- EC-V-4. Узкий экран (375px) → полоса переносит кнопку под число (`flex-wrap`), без
  горизонтального скролла.

### Критерии приёмки

- AC-V-1. При `lessonsLeft <= LOW_BALANCE_THRESHOLD` в полосе видны бейдж и кнопка «Пополнить»;
  клик открывает `AddPackage` (модалка с блюром, по §7).
- AC-V-2. При здоровом балансе кнопки/бейджа нет.
- AC-V-3. Полоса видна на всех четырёх вкладках; новых сетевых запросов на non-overview
  вкладках не добавилось (INV-X2).
- AC-V-4. Светлая и тёмная темы: тинт `warning` читается в обеих (нет сырых цветов).
- AC-V-5. 375px: кнопка переносится, скролла по горизонтали нет.

Псевдокод: `02_vitals-strip.md`.

## 5. H — шапка и пустые состояния-CTA

**Проблема.** Самая заметная кнопка шапки — редкое «Редактировать». Частые действия спрятаны.
Пустой next-lesson («Урок не запланирован») — мёртвый текст без действия.

### Функциональные требования

- FR-H-1. Primary-действие шапки = `AddLesson` (studentId + lessonsLeft) — частотное «добавить
  урок». Рендерится в правом кластере шапки **перед** меню «···».
- FR-H-2. «Редактировать» уходит из шапки в меню «···» (`StudentActionsMenu`) отдельным пунктом
  над «Скопировать ссылку».
- FR-H-3. Открытие редактирования из пункта меню реализуется **контролируемым**
  `EditStudentDialog`: пункт меню переключает внешний `open`, диалог рендерится сиблингом меню
  (не вложен в `DropdownMenuItem`) — устранение конфликта фокуса Radix Dialog-в-DropdownMenu.
  `EditStudentDialog` получает опциональные `open?`/`onOpenChange?` (контролируемый режим);
  без них — текущее самоуправление (обратная совместимость со «+ добавить контакт» в обзоре).
- FR-H-4. Пустой next-lesson в обзоре (`t.students.overview.noNextLesson`) дополняется CTA
  `AddLesson` — «запланировать», вместо мёртвого текста.
- FR-H-5. Пустые состояния списков (`lessons`/`packages`/`payments`/`homework`) **уже** имеют
  кнопку «Добавить…» в шапке секции рядом — отдельный CTA в `EmptyState` им не обязателен;
  допускается проброс `action` в `EmptyState` для усиления (опционально, не ломает §8).

### Инварианты

- INV-H-1. Деструктив (удаление) остаётся под подтверждением и визуально отделён в меню
  (`text-destructive`) — поведение не ослабляем.
- INV-H-2. `EditStudentDialog` в самоуправляемом режиме (без пропов `open`) работает как
  раньше — потребитель «+ добавить контакт» (`student-overview.tsx`) не трогаем.

### Краевые случаи

- EC-H-1. Клик «Редактировать» в меню → меню закрывается, модалка открывается (фокус
  переходит в модалку, не теряется). ESC/оверлей закрывают модалку (Radix).
- EC-H-2. `AddLesson` в шапке без `lastLessonAt` → дефолт даты «завтра» (`defaultStartDate`
  уже это умеет). Хинт баланса показывается из `lessonsLeft`.
- EC-H-3. Узкий экран: правый кластер шапки переносится (`flex-wrap`, уже есть) — primary
  «+ урок» + «···» помещаются.

### Критерии приёмки

- AC-H-1. В шапке первичная кнопка — «Добавить урок»; «Редактировать» доступно только из «···».
- AC-H-2. Клик «Редактировать» в меню открывает модалку редактирования; сохранение работает
  как раньше; фокус-трап и ESC работают (EC-H-1).
- AC-H-3. Пустой next-lesson показывает кнопку «Запланировать», открывающую `AddLesson`.
- AC-H-4. «+ добавить контакт» в обзоре по-прежнему открывает редактирование (регресс INV-H-2).
- AC-H-5. Адаптив 375px: шапка не даёт горизонтального скролла.

Псевдокод: `03_header-and-empty-ctas.md`.

## 6. L — раскладка обзора в две колонки (`lg+`)

**Проблема.** На десктопе обзор — один узкий столбец, ширина простаивает; для ежедневного
инструмента это заметно. Витальное и идентичность (контакты/ссылка) свалены в один поток.

### Функциональные требования

- FR-L-1. Контент вкладки overview оборачивается в адаптивную сетку: на `lg+` — две колонки
  (`grid gap-6 lg:grid-cols-3`), на `< lg` — один столбец (мобайл-ферст, `docs/DESIGN.md` §4).
- FR-L-2. **Главная колонка** (`lg:col-span-2`): зона внимания (A) → карточка next-lesson →
  недавняя активность.
- FR-L-3. **Aside** (`lg:col-span-1`): вторичные KPI (to-review, paid) → контакты → ссылка
  ученика.
- FR-L-4. next-lesson повышается из KPI-плитки в самостоятельную карточку главной колонки
  (с CTA из FR-H-4). To-review и Paid остаются как компактные навигационные плитки в aside.
- FR-L-5. Шапка, витальная полоса и табы остаются на полную ширину **над** сеткой (не входят в
  две колонки). Другие вкладки (списки) — без изменений (они уже одностолбцовые списки).
- FR-L-6. Порядок DOM на мобильном = порядок чтения: внимание → next-lesson → KPI → контакты →
  ссылка → активность (Tab-порядок совпадает с визуальным, §9).

### Инварианты

- INV-L-1. Видимое содержимое обзора не теряется — только перераспределяется по колонкам.
- INV-L-2. Загрузка данных не меняется (та же `getStudentOverview`).

### Краевые случаи

- EC-L-1. 768px (планшет, до `lg`) → один столбец, порядок FR-L-6.
- EC-L-2. Нет контактов/активности → соответствующие блоки aside/колонки не пустуют визуально
  (контакты дают «+ добавить контакт», активность скрывается как сейчас).
- EC-L-3. 1440px → две колонки в пределах `container` (max 1400px), без растекания строк
  (длинный текст ограничен, §3).

### Критерии приёмки

- AC-L-1. На `lg+` обзор — две колонки по FR-L-2/L-3; на `< lg` — один столбец в порядке FR-L-6.
- AC-L-2. next-lesson — карточка главной колонки с CTA при пустом.
- AC-L-3. Контакты и ссылка — в aside; видны и кликабельны (фокус виден).
- AC-L-4. Скролла по горизонтали нет на 375/768/1024/1440.

> **Отклонённая альтернатива (зафиксировано).** Полностью убрать вкладку overview и сделать
> «посадку» без таба — **отклонено**: сломает ленивую загрузку по `?tab=` (perf-P3) либо
> заставит грузить все списки сразу (регресс производительности). Tab-модель остаётся; overview
> — дешёвая посадочная вкладка.

## 8. Стратегия тестирования (TDD)

Раннер — **vitest** (`pnpm test`); стиль — юнит-тесты чистых функций (см. `overview.test.ts`,

выносим в чистые хелперы, остальное проверяем ручным сквозным прогоном по критериям приёмки.

| Уровень           | Что                                                                           | Как                                   |

| Юнит (vitest)     | `buildAttentionItems` (порядок FR-A-2, пустота EC-A-1, изоляция INV-A-1)      | дополнение `overview.test.ts`         |

| CI                | `pnpm typecheck && pnpm lint && pnpm test && pnpm build`                      | без `any`, зелёные                    |

Порядок реализации (каждый шаг отгружаем независимо): **V → A → H → L**.

- **V** — самый дешёвый (рестайл + один опциональный проп), мгновенная польза «пополни сейчас».
- **A** — главный UX-выигрыш (чистая функция + 1 COUNT + тесты).
- **H** — средний (рейк шапки + контролируемый диалог, аккуратно с фокусом Radix).
- **L** — чисто раскладка, без данных; финальная полировка десктопа.
