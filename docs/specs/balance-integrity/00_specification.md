# Спецификация — целостность учётного ядра (B1–B4)

Основано на ревью учётного ядра (диалог «анализ багов»). Это фаза **S** (Specification)
SPARC: фиксируем требования, краевые случаи, инварианты и критерии приёмки. Псевдокод —
в файлах `01_*`…`03_*` этой папки.

## 0. Контекст и принципы

Учётное ядро («провёл → списалось 1 занятие») собрано вокруг БД-функций
`complete_lesson` / `reopen_lesson` / `shift_series_lessons` (атомарно, идемпотентно,
`SECURITY INVOKER` под RLS). Это **bug-fix этого ядра**, а не новые денежные фичи: продуктовый
кластер M1–M6 (цены, долги, расчёты) остаётся вне скоупа. Чиним 4 дыры целостности,
выявленные ревью:

| #   | Симптом (простыми словами)                                         | Где                                                   |
| --- | ------------------------------------------------------------------ | ----------------------------------------------------- |
| B1  | «урок из воздуха»: reopen возвращает баланс, которого не списывали | `complete_lesson`, `reopen_lesson` (SQL)              |
| B2  | двойное списание при гонке (двойной клик / ретрай)                 | те же функции (нет блокировки строки урока)           |
| B3  | серия на неск. дней создаётся «наполовину», ретрай → дубли         | `createLessonAction` (цикл из N не-атомарных вставок) |
| B4  | задвоение ДЗ при повторной отправке формы завершения               | `completeLessonAction` (игнор `already_done`)         |

Правила проекта: мутации баланса — в БД-функциях; гарды дублируем на сервере; магические
числа — в `src/lib/constants.ts`; никакого `any`; стек — Next 15 App Router, Supabase, Zod,
vitest. Источник схемы и RLS — только `supabase/migrations/`.

## 1. Глоссарий статусов урока (без изменений)

| Статус      | Смысл            | Баланс    | Терминальный               |
| ----------- | ---------------- | --------- | -------------------------- |
| `scheduled` | запланирован     | не списан | нет                        |
| `done`      | проведён         | списано 1 | да                         |
| `no_show`   | ученик не пришёл | списано 1 | да                         |
| `canceled`  | отменён          | не списан | нет (можно реактивировать) |

## 2. B1 — «чек» списания на уроке (точная инверсия reopen)

**Проблема.** `complete_lesson` и `reopen_lesson` не хранят, **был ли списан** конкретный урок и
**с какого пакета**. Каждая функция угадывает по агрегату пакетов, и угадывает асимметрично:

- списание срабатывает при `lessons_left > 0` (иначе не списывает ничего);
- возврат срабатывает при `lessons_left < total_lessons` (пакет `0/N` под это подходит).

Поэтому «завершил при нулевом балансе → переоткрыл» **создаёт +1 занятие из ничего**
(см. AC-B1-1).

### Функциональные требования

- FR-B1-1. Новый столбец `lesson.charged_package_id uuid` (FK → `package.id`,
  `on delete set null`): «чек» — с какого пакета списан этот урок. `NULL` = не списывался.
- FR-B1-2. `complete_lesson` при списании проставляет `charged_package_id = <пакет>` в той же
  `UPDATE lesson`. Если списывать было нечего (нет пакета с балансом) → `charged_package_id` остаётся `NULL`.
- FR-B1-3. `reopen_lesson` возвращает занятие **только если `charged_package_id` задан** и
  **ровно в тот же пакет**; затем обнуляет `charged_package_id`. Возврат клампится
  `least(lessons_left + 1, total_lessons)`.
- FR-B1-4. Если пакет-«чек» удалён к моменту reopen (`charged_package_id` обнулён FK) → возврат
  не делаем (нечего и некуда возвращать) — безопасная сторона.
- FR-B1-5. Сигнатуры RPC `complete_lesson(uuid,text,text,text)` / `reopen_lesson(uuid)` и их
  JSON-ответы **не меняются** (код приложения не трогаем).

### Инварианты

- INV-B1-1. `0 <= lessons_left <= total_lessons` сохраняется всегда.
- INV-B1-2. **Суммарный баланс ученика после `complete` затем `reopen` равен балансу до
  `complete`** — при любом числе пакетов и при нулевом балансе (точная инверсия).
- INV-B1-3. Любой урок не из `(done,no_show)` при `reopen_lesson` не меняет баланс.

### Краевые случаи

- EC-B1-1. Завершение при балансе 0 → `charged_package_id = NULL`; последующий reopen → баланс
  остаётся 0 (это и есть фикс «урока из воздуха»).
- EC-B1-2. Несколько пакетов: списание с старого (`order by created_at asc`), но «чек» хранит
  именно его → reopen возвращает в тот же старый пакет (раньше возврат шёл в «самый свежий»).
- EC-B1-3. Пакет-«чек» удалён между complete и reopen → reopen без возврата, без ошибки.

### Миграция данных (legacy-уроки)

Существующие терминальные уроки чека не имеют. Рекомендация (решение спеки):
**best-effort backfill — `charged_package_id` = самый старый пакет ученика** (`order by created_at asc`),
т.к. старое списание всегда шло со старого пакета. Это сохраняет дореформенное поведение reopen
для существующих данных; «урок из воздуха» возможен лишь для редких legacy-уроков, завершённых
при овердрафте (они и так были багом). Если в проде ещё нет реальных уроков — backfill = no-op.
Backfill **не меняет** текущие балансы (ставит только указатель).

### Критерии приёмки

- AC-B1-1 (главный, репро бага). Пакет `total=4,left=0`; урок `scheduled` → `complete` →
  баланс 0 → `reopen` → **баланс 0** (было: 1).
- AC-B1-2. Пакет `total=8,left=8`; `complete` → 7 → `reopen` → 8 (точная инверсия).
- AC-B1-3. `no_show` ведёт себя как `done` в AC-B1-1/2.
- AC-B1-4. Два пакета (старый `4/4`, новый `2/2`): `complete` (спишет со старого → `3/4`) →
  `reopen` → старый снова `4/4`, новый `2/2`.
- AC-B1-5. RPC-ответы и поведение UI без изменений (баланс, баннер low-balance).

## 3. B2 — блокировка строки урока (нет двойного списания)

**Проблема.** Чтение статуса урока идёт `SELECT … INTO` **без `FOR UPDATE`**; защита от повтора
опирается на это устаревающее чтение. Два одновременных вызова на один урок оба видят
`scheduled`, оба проходят guard, `UPDATE` без предиката статуса выполняется дважды → **списано 2
кредита за 1 урок**. Тот же риск у `reopen_lesson` (двойной возврат).

### Функциональные требования

- FR-B2-1. В начале `complete_lesson` и `reopen_lesson` читать строку урока с `FOR UPDATE`.
- FR-B2-2. Второй параллельный вызов ждёт на блокировке, перечитывает уже терминальный статус и
  попадает в идемпотентную заглушку (без второго списания/возврата).
- FR-B2-3. Реализуется **в той же миграции 0010**, что и B1 (обе функции и так переписываются).

### Инвариант

- INV-B2. Один урок списывает/возвращает **ровно один** кредит, сколько бы конкурентных вызовов
  ни пришло.

### Критерии приёмки

- AC-B2-1. Два одновременных `complete_lesson(L)` → суммарно списан 1 кредит (не 2).
- AC-B2-2. Два одновременных `reopen_lesson(L)` → возвращён 1 кредит (не 2).
  (Проверяется сценарием с двумя сессиями psql; см. `01_charge-receipt.md` → TDD.)

## 4. B3 — атомарное создание серии (нет «половины» расписания)

**Проблема.** `createLessonAction` (ветка повтора) в цикле по дням недели делает на каждый день
`insert lesson_series` + `insert lesson[]` — **2·N не-атомарных операций**. Сбой на полпути
оставляет уже созданные дни в БД; пользователь видит ошибку и пересоздаёт → дубли.

### Функциональные требования

- FR-B3-1. Новая БД-функция `create_lesson_series(p_student_id uuid, p_series jsonb)` создаёт
  **все** серии и **все** их уроки в **одной транзакции** (всё или ничего). `SECURITY INVOKER` →
  RLS `*_insert` (`owns_student`) и триггер `set_tutor_id_from_student` применяются как обычно.
- FR-B3-2. `createLessonAction` формирует JSON (серии + их даты) и делает **один** `rpc`-вызов
  вместо цикла вставок. Проверка пересечений по времени (`findLessonConflict`) остаётся в action
  **до** вызова RPC (она читает чужие уроки — хорошо ложится на TS под RLS).
- FR-B3-3. Поведение ветки «Не повторять» (одиночные уроки, без серии) — **не меняется**.
- FR-B3-4. Пустой `p_series` (нет дат) → no-op.

### Инвариант

- INV-B3. После `createLessonAction` в БД либо **все** запрошенные серии и уроки, либо **ничего**
  (повтор после сбоя безопасен — дублей не появляется).

### Критерии приёмки

- AC-B3-1. Серия пн+чт ×8: успех → 2 серии + все уроки, конфликт-чек отрабатывает как раньше.
- AC-B3-2. Искусственный сбой на второй серии → в БД **ноль** новых серий/уроков (rollback).
- AC-B3-3. Повтор после сбоя → ровно один комплект (нет дублей понедельников).

## 5. B4 — гард повторного создания ДЗ при завершении

**Проблема.** `completeLessonAction` создаёт ДЗ всегда при заполненном `title`, игнорируя
`already_done` из RPC. Повторная отправка формы (двойной сабмит) → урок не спишется повторно
(идемпотентно), а **ДЗ задвоится**.

### Функциональные требования

- FR-B4-1. `completeLessonAction` читает `already_done` из ответа `complete_lesson` и создаёт ДЗ
  **только если `already_done !== true`** (т.е. это реальное первое завершение).
- FR-B4-2. Чисто серверная правка, без миграции и без изменения UI/типов схемы.

### Критерии приёмки

- AC-B4-1. Двойная отправка формы завершения с `title` → создаётся **одна** ДЗ.
- AC-B4-2. Обычное первое завершение с `title` → ДЗ создаётся (регресс не вносим).

## 7. Стратегия тестирования (TDD)

Раннер — **vitest** (`pnpm test`), стиль — юнит-тесты чистых функций. БД-функции и серверные
actions напрямую не юнит-тестируются (нет DB-харнесса), поэтому:

| Уровень           | Что                                                                         | Как                                           |
| ----------------- | --------------------------------------------------------------------------- | --------------------------------------------- |
| Контракт БД       | инварианты B1 (вкл. AC-B1-1 «урок из воздуха»), гонка B2, rollback B3       | psql-сценарии в `01_*`/`02_*` (будущий pgTAP) |
| Юнит (vitest)     | сборка JSON-полезной нагрузки для `create_lesson_series` (чистый хелпер B3) | новый `*.test.ts`                             |
| Сквозной (ручной) | reopen-флоу (B1), создание серии (B3), двойной сабмит ДЗ (B4)               | чек-лист из критериев приёмки                 |
| CI                | `pnpm typecheck && pnpm lint && pnpm test && pnpm build`                    | без `any`, зелёные                            |
