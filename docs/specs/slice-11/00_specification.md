# Срез 11 — спецификация (приоритет «сейчас»)

Фаза **S** (Specification) SPARC: контекст, требования, инварианты, критерии приёмки
и TDD-якоря. Псевдокод и модули реализации — в файлах `01`–`03`. Это тонкий
следующий срез после срез 10 ([ADR-0003](../../decisions/0003-admin-role.md)).

Срез собирает три независимых тонких пункта, отобранных как «делаем сейчас» — те,
что дают максимум пользы **без пересечения границ PII** ADR-0003 и **без нового
ADR**:

| #   | Пункт                                                                                | Зона             | Модуль                                           |
| --- | ------------------------------------------------------------------------------------ | ---------------- | ------------------------------------------------ |
| 1   | Динамический служебный дашборд (дельты, уроки по статусам, сигналы активации/оттока) | `features/admin` | [`01_dashboard-stats.md`](01_dashboard-stats.md) |
| 2   | Самостоятельное восстановление пароля («забыли пароль»)                              | `features/auth`  | [`02_forgot-password.md`](02_forgot-password.md) |
| 3   | Инбокс: фильтр по категории + счётчики по табам                                      | `features/admin` | [`03_feedback-inbox.md`](03_feedback-inbox.md)   |

## Контекст и цель

После среза 10 (служебная роль администратора) дашборд показывает 4 статичных
счётчика, а инбокс фильтруется только по статусу. Параллельно в продуктовом ядре
обнаружилась дыра: walking-skeleton шаг 1 — «репетитор регистрируется и **входит**»
— не имеет пути восстановления доступа (в [auth/actions.ts](../../../src/features/auth/actions.ts)
есть только `signIn/signUp/signOut`). Репетитор, забывший пароль, теряет аккаунт.

Срез закрывает три эти доделки, оставаясь тонким (правила проекта).

## Связь с ADR-0003 (почему без нового ADR)

- **Пункт 1 (дашборд)** — строго в рамках санкционированной эволюции ADR-0003:
  «деньги добавляются позже **отдельным ключом**, без новой инфраструктуры» и
  «дашборду хватает счётчиков». Все новые метрики — **агрегаты (COUNT)**, считаются
  внутри gated `admin_stats()` (`SECURITY DEFINER` + `if not is_admin() then raise`).
  **Ни одной строки** `student/lesson/payment` за пределы БД не уходит. Инвариант
  «админ не получает построчного доступа к данным учеников» сохраняется.
- **Пункт 3 (инбокс)** — категория уже в схеме `feedback` (`0006`), админ уже читает
  строки `feedback` по RLS (`feedback_select_admin`). Добавляются только новое
  измерение фильтра и агрегатные счётчики. Границы не двигаются.
- **Пункт 2 (восстановление пароля)** — продуктовая auth-фича для **самого**
  пользователя (не админская операция над чужим аккаунтом). Стандартный флоу
  Supabase Auth: **без изменения схемы/RLS**, без новой поверхности доступа,
  без service-role. Поэтому ADR не нужен.

> ⛔ Чего этот срез сознательно **не** делает (это были бы 🔴-пункты, требующие
> ADR-0004): управление репетиторами (деактивация/бан), **админский** сброс чужого
> пароля, резолв email отправителя в инбоксе, ответы из приложения. См. «Вне скоупа».

## Текущее состояние (as-is)

- **Дашборд:** [admin/page.tsx](<../../../src/app/(admin)/admin/page.tsx>) рисует
  `AdminStatsCards` из `getAdminStats()` → RPC `admin_stats()` (4 ключа:
  `tutors/students/lessons/feedback_new`, миграция `0012`).
- **Инбокс:** [feedback/page.tsx](<../../../src/app/(admin)/admin/feedback/page.tsx>) +
  `FeedbackFilterTabs` фильтруют по `?status=` (`all|new|seen|closed`). Категория
  (`bug|idea|question|other`) хранится, но не фильтруется и не агрегируется.
- **Auth:** маршруты `(auth)/login`, `(auth)/signup`. Нет `/forgot-password`,
  `/reset-password`, нет route-handler `/auth/callback`. Middleware
  ([middleware.ts](../../../src/lib/supabase/middleware.ts)) уже whitelist-ит
  `PUBLIC_PREFIXES = ["/login","/signup","/s/","/auth"]`.
- **Правила пароля** — единый источник `PASSWORD_RULES` в
  [auth/schema.ts](../../../src/features/auth/schema.ts) (переиспользуем при сбросе).
- **Email:** `resend` есть в зависимостях, но **нигде не используется**
  (только `env.resendApiKey`). Письма восстановления идут через **встроенную почту
  Supabase Auth** (см. модуль 2), а не через app-слой Resend.
- **Lesson.status** ∈ `scheduled | done | canceled | no_show` (`0001`, `0004`).
- Типы БД — `src/lib/supabase/database.types.ts`, пишутся **руками** «to match
  migrations».

## Общие инварианты (что НЕЛЬЗЯ сломать)

- **Источник схемы и прав — `supabase/migrations/`.** Новые RPC/ключи — только
  миграцией (`0013`); через MCP схему/RLS не меняем.
- **Дашборд видит только агрегаты.** Никакого построчного `SELECT` на
  `student/lesson/payment/tutor`. Новые метрики — `COUNT`/`COUNT FILTER` внутри
  gated функции.
- **Трёхслойная защита админ-зоны** (middleware → `assertAdmin` → БД-гейт) не
  ослабляется. Не-админ получает `forbidden` из RPC.
- **`feedback_insert` сохраняется** — кнопка «Поддержка» работает как раньше для всех.
- **Восстановление пароля не раскрывает существование email** — ответ всегда
  «если такой email есть — мы отправили ссылку» (anti-enumeration).
- **Бизнес-логика не в компонентах** (правила проекта): данные/мутации — в
  `queries.ts`/`actions.ts`; Supabase только через `lib/supabase/*`.
- **Все строки UI — через `t.*`**; цвета — токены; иконки — lucide; UI по
  `docs/DESIGN.md` (light/dark, адаптив, фокус-ринг, состояния loading/empty/error).
- **TypeScript strict, без `any`.** Тонкие модули, одна ответственность.

## Нефункциональные требования

- Состояния `loading`/`empty`/`error` на каждом новом экране.
- Адаптив 375/768/1024/1440; контраст ≥4.5:1; видимый фокус.
- `pnpm typecheck && pnpm lint && pnpm test && pnpm build` — зелёные.
- Новая логика покрыта unit-тестами (vitest, чистые функции; БД не трогаем в тестах).

## Вне скоупа (тонко, на потом — это уже 🔴, нужен ADR-0004)

Управление репетиторами (деактивация/бан/удаление через Supabase Auth admin) ·
**админский** сброс чужого пароля (recovery-ссылка от лица админа) · аудит-лог
админских действий · резолв email/имени отправителя в инбоксе · ответы на обращения
из приложения · деньги/MRR/активные пакеты на дашборде (отдельный ключ позже) ·
графики/charting-либа (начинаем с чисел и дельт) · брендированное письмо
восстановления через Resend (хватает встроенного письма Supabase) · поиск по тексту
обращений · импersonation «войти как репетитор».
