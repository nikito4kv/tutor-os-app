# Спецификация — стриминг дашборда через `<Suspense>`

Фаза **S** (Specification) SPARC: требования, инварианты и критерии приёмки.
Псевдокод и план миграции — в [`01_pseudocode.md`](01_pseudocode.md).

## Контекст и цель

`src/app/(app)/dashboard/page.tsx` помечен `export const dynamic = "force-dynamic"`
(данные «как сейчас», кэш не нужен) и вызывает один агрегатор
`getDashboardData()`, который **в одном `Promise.all`** делает 8 запросов и мёрджит
имена учеников локально. Страница ждёт **все** запросы до первого байта.

`loading.tsx` есть, но он закрывает только переход по роуту (route transition);
**внутри** страницы первый рендер блокируется самым медленным запросом, и все
карточки появляются одновременно.

**Цель:** дать карточкам стримиться независимо через `<Suspense>` — оболочка и
скелеты отдаются мгновенно, каждая карточка дорисовывается по мере готовности
своих данных. Поведение, данные и визуал **не меняются**.

Честная оговорка: на данных **одного репетитора** запросы быстрые и параллельные,
так что выигрыш по времени умеренный. Ценность растёт с объёмом данных и при
медленном одиночном запросе (например, баланс/пакеты по многим ученикам). Делаем
аккуратно и недорого; если по бенчмаркам выгода околонулевая — это допустимый
исход, фиксируем и не усложняем.

## Текущий поток (as-is)

`getDashboardData()` (`src/features/dashboard/queries.ts`) параллельно тянет:

```
listStudentOptions()                         → имена (шарятся 4 карточками)
getNextLesson()                              → NextLessonCard
listLessonsInRange(dayStart, dayEnd)         → TodayLessons
listOverdueLessons()                         → ActionInbox
listHomeworkToReview()                       → ActionInbox
listOverdueHomework()                        → ActionInbox
listPackageBalances()                        → LowBalanceStudents (+ aggregate)
listPaymentAmountsInRange(month.from, to)    → MonthIncomeCard
getCurrentTutor()                            → валюта (MonthIncomeCard); уже cache()
```

Карточки сейчас — **чистые presentational-компоненты**, принимают готовые props
(`NextLessonCard`, `MonthIncomeCard`, `TodayLessons`, `ActionInbox`,
`LowBalanceStudents`). Это удобно: presentational-слой оставляем как есть и
тестируемым (`aggregate.ts` + `aggregate.test.ts` — чистые хелперы — не трогаем).

## Карта зависимостей данных по карточкам

| Карточка             | Свои запросы                                                          | Нужны имена учеников? | Нужна валюта?          |
| -------------------- | --------------------------------------------------------------------- | --------------------- | ---------------------- |
| `NextLessonCard`     | `getNextLesson`                                                       | да                    | нет                    |
| `MonthIncomeCard`    | `listPaymentAmountsInRange`                                           | нет                   | да (`getCurrentTutor`) |
| `TodayLessons`       | `listLessonsInRange(today)`                                           | да                    | нет                    |
| `ActionInbox`        | `listHomeworkToReview` + `listOverdueLessons` + `listOverdueHomework` | да                    | нет                    |
| `LowBalanceStudents` | `listStudentOptions` + `listPackageBalances`                          | (сами и есть)         | нет                    |

**Общие данные:** имена учеников (`listStudentOptions`) нужны 4 карточкам, валюта
(`getCurrentTutor`) — 1. Если просто разнести запросы по карточкам, `listStudentOptions`
выполнится несколько раз → регресс (N запросов вместо одного).

## Решение

1. **`<Suspense>`-границы** вокруг каждой карточки (или группы) в `page.tsx`.
2. Каждая карточка получает **тонкий async-загрузчик** (server component), который
   тянет свой срез и рендерит существующий presentational-компонент.
3. **Дедупликация общих данных** через React `cache()`:
   - обернуть `listStudentOptions` в `cache()` (или создать `getStudentNamesMap()`
     с `cache()` в зоне dashboard) — выполнится **один раз на запрос**, сколько бы
     карточек её ни звали;
   - `getCurrentTutor` уже обёрнут `cache()` (`src/lib/auth.ts`) — переиспользуем.
4. Fallback каждой границы — скелет, переиспользующий куски нынешнего `loading.tsx`.

Так агрегатор `getDashboardData()` распадается на независимые загрузчики, но
число обращений к БД остаётся прежним (общие — закэшированы в рамках запроса).

## Инварианты (что НЕЛЬЗЯ сломать)

- **Те же данные в каждой карточке**, тот же мёрдж имён (`nameById`), та же
  логика low-balance (`selectLowBalanceStudents`) и суммы (`sumAmounts`).
- **Число запросов к БД не растёт** относительно as-is (общие данные — `cache()`).
- `force-dynamic` сохраняется (дашборд — «как сейчас», без кэша рендера).
- Presentational-компоненты карточек и их props **не меняются** (только обёрнуты
  загрузчиками).
- RLS-scoping каждого запроса сохраняется (запросы те же).
- Каждая карточка имеет состояния loading (skeleton) / empty / error
  (`docs/DESIGN.md`, правила проекта). Empty уже внутри карточек; loading даёт
  Suspense-fallback; error — см. ниже.

## Нефункциональные требования

- TypeScript strict, без `any`. Тексты через `t.*`.
- Загрузчики тонкие (< ~40 строк), вся вычисляемая логика — в `aggregate.ts`.
- `typecheck`, `lint`, `test`, `build` зелёные.

## Критерии приёмки (Definition of Done)

- [ ] Каждая карточка обёрнута в `<Suspense>` со своим скелетом; оболочка
      (заголовок + сетка) рендерится мгновенно.
- [ ] `listStudentOptions` вызывается **один раз на запрос** (проверить, что
      `cache()` дедуплицирует — например, временный лог/счётчик в dev или
      инспекция сети Supabase).
- [ ] Данные во всех карточках идентичны прежним (визуальный diff = 0).
- [ ] `loading.tsx` либо переиспользует те же скелеты, либо остаётся как route-fallback.
- [ ] `pnpm typecheck && pnpm lint && pnpm test && pnpm build` зелёные.
- [ ] `aggregate.test.ts` проходит без правок.

## TDD-якоря / план проверки

- **Юнит (vitest):** чистая логика уже покрыта `aggregate.test.ts`
  (`selectLowBalanceStudents`, `sumAmounts`). Сплит не меняет эти функции — тесты
  должны остаться зелёными **без правок** (это и есть якорь-регресс).
- **Дедупликация:** проверить, что общие данные не множат запросы. Варианты:
  временный счётчик вызовов в обёртке (убрать перед мерджем) или инспекция
  сетевых запросов к Supabase в dev.
- **e2e/ручной (Playwright):**
  1. Дашборд с данными → все 5 карточек появляются (стримингом), значения верны.
  2. Пустой аккаунт → во всех карточках корректные empty-состояния.
  3. Медленный одиночный запрос (можно сэмулировать задержку) → остальные
     карточки уже видны, не блокируются.
  4. Ошибка одной карточки (см. ниже) не роняет всю страницу.

## Открытый вопрос для phase 2: обработка ошибок карточки

Сейчас при throw в `getDashboardData()` падает весь дашборд (ловит `error.tsx`).
При сплите можно изолировать сбой одной карточки локальной обёрткой
(`<ErrorBoundary>`/`error`-ветка внутри загрузчика → `<ErrorState/>`), чтобы
остальные жили. Это **желательно, но опционально** для MVP — финальное решение
фиксируется в phase 2. По умолчанию: оставить общий `error.tsx`, изоляцию сделать
только если она дешёвая.

## Вне скоупа

- Кэширование/ISR дашборда (остаётся `force-dynamic`).
- Изменение запросов, схемы, RLS, агрегаций.
- Редизайн карточек.
