# Спецификация — правки флоу урока (C1, C2, C3) + полировка (L1–L4)

Основано на утверждённом плане работ.
Это фаза **S** (Specification) SPARC: фиксируем требования, краевые случаи, инварианты и
критерии приёмки. Псевдокод — в файлах `01_*`…`04_*` этой папки.

## 0. Контекст и принципы

Учётное ядро («провёл → списалось 1 занятие») собрано вокруг БД-функций
`complete_lesson`/`shift_series_lessons` (атомарно, идемпотентно, `SECURITY INVOKER` под RLS).
Эти правки закрывают краевые дыры ядра завершения и полируют мелочи. Денежный кластер
(M1–M6) **вне скоупа** — отдельный продуктовый разговор.

Правила проекта: мутации баланса — в БД-функциях; гарды дублируем на сервере; UI-тексты
через `t.*` (`src/lib/i18n/ru.ts`); магические числа — в `src/lib/constants.ts`; никакого `any`;
состояния loading/empty/error; стек — Next 15 App Router, Supabase, Zod, vitest.

## 1. Глоссарий статусов урока

| Статус      | Смысл            | Баланс    | Терминальный               |
| ----------- | ---------------- | --------- | -------------------------- |
| `scheduled` | запланирован     | не списан | нет                        |
| `done`      | проведён         | списано 1 | да                         |
| `no_show`   | ученик не пришёл | списано 1 | да                         |
| `canceled`  | отменён          | не списан | нет (можно реактивировать) |

«Терминальный» = занятие уже списано с баланса.

## 2. C1 — гард отмены урока

**Проблема.** `cancelLessonAction` переводит урок в `canceled` без проверки текущего статуса,
тогда как `deleteLessonAction`/`updateLessonAction` фильтруют `status in (scheduled, canceled)`.

### Функциональные требования

- FR-C1-1. Отменить (`canceled`) можно **только** урок в статусе `scheduled`.
- FR-C1-2. Вызов на терминальном (`done`/`no_show`) уроке **не меняет** ни статус, ни баланс.
- FR-C1-3. Поведение для серий (`cancelSeriesAction`) не меняется — там фильтр уже есть.
- FR-C1-4. Ошибок наружу не добавляем: если строк не затронуто — это no-op, не throw
  (RLS/гард уже скрывают чужое и терминальное).

### Инвариант

- INV-C1. Ни одна отмена не должна затрагивать урок, с которого списан баланс.

### Критерии приёмки

- AC-C1-1. Прямой вызов `cancelLessonAction(doneLessonId, …)` → статус остаётся `done`,
  баланс не меняется.
- AC-C1-2. `cancelLessonAction(scheduledLessonId, …)` → статус `canceled`.
- AC-C1-3. UI ветка «Отменить» по-прежнему видна только для `scheduled` (регресс не вносим).

## 3. C2 — обратимое «Завершить» / «Не пришёл» (reopen)

**Проблема.** Терминальный статус необратим: случайный тап «Завершить»/«Не пришёл» сжигает
занятие навсегда; единственный «откат» — удаление пакета (разрушительно).

### Функциональные требования

- FR-C2-1. Новая БД-функция `reopen_lesson(p_lesson_id uuid)` атомарно возвращает урок в
  `scheduled` и **возвращает 1 занятие** в пакет.
- FR-C2-2. **Идемпотентность.** Повторный вызов на уже не-терминальном уроке —
  no-op без второго возврата занятия (зеркало идемпотентности `complete_lesson`).
- FR-C2-3. **Выбор пакета для возврата:** самый свежий пакет (`order by created_at desc`),
  где `lessons_left < total_lessons`, с `for update`. Если такого нет (нет пакетов или все
  полные) — занятие не возвращаем (зеркалит ситуацию, когда списания при 0 не было).
- FR-C2-4. `topic`/`note` урока сохраняются (это рабочий черновик, не сбрасываем).
- FR-C2-5. Привязанное ДЗ, созданное при завершении, **остаётся** (независимая сущность);
  текст подтверждения сообщает об этом.
- FR-C2-6. `SECURITY INVOKER` (default) → RLS скоупит к владельцу; чужой урок = «не найден».
- FR-C2-7. Серверное действие `reopenLessonAction(lessonId, studentId)` вызывает RPC,
  делает `revalidateLesson(studentId)` и возвращает `{ ok, lessonsLeft, error? }`.
- FR-C2-8. UI: в карточке урока (`ViewMode`) для терминального урока появляется кнопка
  «Вернуть в запланированные» с шагом подтверждения; при успехе модалка закрывается.

### Инварианты

- INV-C2-1. `0 <= lessons_left <= total_lessons` сохраняется после reopen (возврат только
  в пакет с местом).
- INV-C2-2. `complete_lesson` затем `reopen_lesson` затем `complete_lesson` → итоговый баланс
  как после одного завершения (нет дрейфа при чередовании, в пределах одного пакета).
- INV-C2-3. Любой урок, не находящийся в `(done,no_show)`, при `reopen_lesson` не меняет баланс.

### Краевые случаи

- EC-C2-1. Урок уже `scheduled`/`canceled` → no-op, вернуть текущий суммарный баланс.
- EC-C2-2. У ученика нет пакетов → статус → `scheduled`, баланс остаётся 0.
- EC-C2-3. Все пакеты полные (`lessons_left == total_lessons`) → статус меняется, занятие
  не добавляем (иначе нарушим INV-C2-1).
- EC-C2-4. Несколько пакетов: списание шло со старого, возврат идёт в свежий с местом —
  для одного пакета это точная инверсия; для нескольких допустимо лёгкое «перемешивание»
  между пакетами, суммарный баланс корректен.
- EC-C2-5. Урок другого тьютора → RLS прячет → `lesson_not_found`.

### Критерии приёмки

- AC-C2-1. Пакет(1) → complete → баланс 0 → reopen → баланс 1, статус `scheduled`.
- AC-C2-2. Повторный reopen → баланс остаётся 1 (идемпотентно).
- AC-C2-3. То же для `no_show`.
- AC-C2-4. reopen без пакетов → статус `scheduled`, баланс 0, без ошибки.
- AC-C2-5. RPC требует новую миграцию `0008_reopen_lesson.sql`, применённую на удалённый
  Supabase.

## 4. C3 — индикатор просроченных уроков

**Проблема.** Запланированный урок с прошедшим временем визуально не отличается от будущего;
ядро «провёл → списалось» тихо проваливается при забывчивости.

### Функциональные требования

- FR-C3-1. Чистая функция `isLessonOverdue(lesson, now)` → `true`, когда
  `status === "scheduled" && starts_at < now`. Единый источник правды для всех вьюх.
- FR-C3-2. В сетке недели (`week-calendar.tsx`) и в списке (`lesson-list.tsx`) просроченный
  урок показывает пометку `t.lessons.overdue` («Пора завершить»), визуально отличимую от
  обычного `scheduled`.
- FR-C3-3. История (`order="desc"`) содержит только не-`scheduled` уроки — её не трогаем.
- FR-C3-4. (Опционально, отдельный шаг) баннер на `/schedule` «N уроков ждут завершения»,
  посчитанный из уже загруженного списка.

### Краевые случаи

- EC-C3-1. Урок ранее сегодня (9:00 при текущем 15:00) — просрочен (сравнение по времени, не дню).
- EC-C3-2. Урок ровно «сейчас»/в будущем — не просрочен.
- EC-C3-3. `canceled`/`done`/`no_show` в прошлом — не просрочены (только `scheduled`).
- EC-C3-4. Время считается наивно в локальной зоне рантайма (как и весь MVP, см. `date.ts`).

### Критерии приёмки

- AC-C3-1. `scheduled` с датой вчера → пометка показана в обеих вьюхах.
- AC-C3-2. `scheduled` завтра → пометки нет.
- AC-C3-3. `canceled` вчера → пометки нет.
- AC-C3-4. Юнит-тесты на `isLessonOverdue` покрывают EC-C3-1…3.

### Вне скоупа

- Реальное напоминание (email/push) — это L5 (сендера в коде нет, MVP помечен ⏳).
- L6 (предупреждение при создании урока задним числом) — не выбран.

## 5. Полировка L1–L4

### L1 — лимит заметки урока

- FR-L1-1. Серверная валидация `note` совпадает со счётчиком формы: max = `LESSON_NOTE_MAX` (200).
- FR-L1-2. `topic` получает собственный явный лимит (200), не общий с `note`.
- AC-L1. Заметка из 201 символа отклоняется на сервере; счётчик `N/200` соответствует.

### L2 — единый порог низкого баланса

- FR-L2-1. `completeLessonAction`/`markNoShowAction` вычисляют `lowBalance` из
  `lessons_left <= LOW_BALANCE_THRESHOLD` (TS-константа), не из поля БД `low_balance`.
- FR-L2-2. В SQL `complete_lesson` оставить `<= 2` + комментарий, что канон — в `constants.ts`.
- AC-L2. Изменение `LOW_BALANCE_THRESHOLD` меняет поведение баннера без правки SQL.

### L3 — цвет дедлайна ДЗ

- FR-L3-1. Чистая функция `isHomeworkOverdue(dueAt, status, now)` →
  `dueAt != null && status !== "reviewed" && dueAt < now`.
- FR-L3-2. Срок красится тревожным (`text-warning`) только при просрочке; иначе нейтрально
  (`text-muted-foreground`). Применяется и у тьютора (`homework-list.tsx`), и на ссылке ученика
  (`s/[token]/page.tsx`).
- FR-L3-3. (Опц.) суффикс `t.homework.overdue` при просрочке.
- AC-L3. Будущий срок — нейтральный цвет; прошедший непроверенный — warning; проверенный — нейтральный.

### L4 — лимит списка уроков на странице ученика (ссылка)

- FR-L4-1. Запрос `upcomingLessons` в `share/queries.ts` ограничен `SHARE_UPCOMING_LIMIT` (10).
- AC-L4. Серия из 52 уроков → на странице ученика не больше 10 ближайших.

## 7. Стратегия тестирования (TDD)

Раннер — **vitest** (`pnpm test`), стиль — юнит-тесты чистых функций (см. `recurrence.test.ts`,
`date.test.ts`). Серверные actions и БД-функции напрямую не юнит-тестируются (нет DB-харнесса),
поэтому логику выносим в чистые хелперы, а БД/actions проверяем ручным сквозным прогоном.

| Уровень           | Что                                                         | Как                                         |
| ----------------- | ----------------------------------------------------------- | ------------------------------------------- |
| Юнит (vitest)     | `isLessonOverdue`, `isHomeworkOverdue`, лимиты схемы (L1)   | новые `*.test.ts`                           |
| Контракт БД       | идемпотентность/инварианты `reopen_lesson`                  | ручной psql / будущий pgTAP, сценарии AC-C2 |
| Сквозной (ручной) | C1 гард, C2 reopen-флоу в UI, C3 пометка, L3 цвет, L4 лимит | чек-лист из критериев приёмки               |
| CI                | `pnpm typecheck && pnpm lint && pnpm test && pnpm build`    | без `any`, зелёные                          |

Порядок реализации: **C1 → L1/L2/L4 (дешёвые, без миграции) → C3 → C2 (миграция последней)**.
Псевдокод по каждому пункту — в `01_cancel-guard.md`, `02_reopen-lesson.md`,
`03_overdue-indicator.md`, `04_polish.md`.
