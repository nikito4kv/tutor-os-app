# Спецификация — производительность под ~100 одновременных пользователей (P1–P4)

Фаза **S** (Specification) SPARC: фиксируем требования, краевые случаи, инварианты и
критерии приёмки по четырём критическим находкам аудита. Псевдокод — в файлах
`01_*`…`04_*` этой папки.

## 0. Контекст и принципы

Аудит выявил четыре места, которые именно **под конкурентной нагрузкой** (≈100 активных
тьюторов + публичные ссылки учеников) превращаются в узкое горло: сетевые N+1, лишние
round-trip к Auth, выборка всего подряд и RLS-функция на каждую строку. Все четыре —
не функциональные баги (фичи работают), а деградация под объёмом данных и параллелизмом.

Цель правок: **снять сетевую и БД-нагрузку без изменения наблюдаемого поведения**.
Ни одна правка не меняет продуктовый флоу — только число запросов и объём выборки.

Правила проекта: бизнес-логика и данные — в `queries.ts`/`actions.ts`, не в
компонентах; единый клиент Supabase через `src/lib/supabase/*`; магические числа — в
`src/lib/constants.ts`; никакого `any`; миграции — единственный источник схемы/RLS; стек —
Next 15 App Router, Supabase, Zod, vitest. Безопасность не ослабляем: RLS остаётся
реальной границей доступа (см. INV-P2 и INV-P4).

## 2. P1 — батч signed URLs вместо N×2 запросов

**Проблема.** `getShareView` и `listHomeworksByStudent` зовут `createHomeworkSignedUrl`
(один HTTP-запрос в Storage) для **каждого** `attachment_url` и `submission_url`. Ученик с
30 ДЗ = до 60 исходящих HTTP-запросов на рендер. Страница `/s/[token]` — `force-dynamic`,
кеша нет → каждое открытие родителем повторяет все 60. При 100 параллельных юзерах это
забивает connection pool и event loop Node.

### Функциональные требования

- FR-P1-1. Новый хелпер `createHomeworkSignedUrls(supabase, paths)` создаёт подписанные
  ссылки **одним** вызовом `storage.from(bucket).createSignedUrls(paths, ttl)` (множественное
  число) и возвращает `Map<path, signedUrl>`.
- FR-P1-2. Пустой/нулевой ввод (нет файлов) → **сетевого вызова нет**, возвращается пустая Map.
- FR-P1-3. `getShareView` и `listHomeworksByStudent` собирают все непустые пути, делают
  **один** батч-вызов, затем разрешают ссылки по Map (отсутствующий путь → `null`).
- FR-P1-4. TTL ссылки выносится в именованную константу `HOMEWORK_SIGNED_URL_TTL_SEC = 3600`
  рядом с `HOMEWORK_BUCKET` в `files.ts` (не инлайн `60 * 60`).
- FR-P1-5. Одиночный `createHomeworkSignedUrl` сохраняется для разовых нужд (после загрузки
  одного файла), но реализуется поверх батча или остаётся тонкой обёрткой — дублирования логики нет.

### Инвариант

- INV-P1. Форма результата (`attachmentSignedUrl`/`submissionSignedUrl` на каждой ДЗ) и порядок
  элементов **не меняются** — рефактор прозрачен для UI.

### Краевые случаи

- EC-P1-1. ДЗ без файлов → обе ссылки `null`, батч-вызова нет (FR-P1-2).
- EC-P1-2. Per-item ошибка подписи одного пути → эта ссылка `null`, остальные валидны (батч
  не падает целиком).
- EC-P1-3. Дубликаты путей в наборе → дедуп перед вызовом; Map разрешает обоих потребителей.
- EC-P1-4. Истёкший/битый путь → `signedUrl` отсутствует в Map → `null` (как сейчас при error).

### Критерии приёмки

- AC-P1-1. Открытие `/s/[token]` ученика с N ДЗ (по 2 файла) делает **1** запрос к Storage на
  подпись, а не 2N (проверка вкладкой Network / счётчиком запросов).
- AC-P1-2. Вкладка «Домашка» в карточке ученика — то же: 1 батч-запрос.
- AC-P1-3. ДЗ без вложений → 0 запросов к Storage, ссылки `null`, страница рендерится.
- AC-P1-4. Юнит-тесты на чистые хелперы `collectHomeworkPaths`/`mergeSignedUrls` (см. `01_*`).

Псевдокод: `01_batch-signed-urls.md`.

## 3. P2 — проверенная серверная авторизация с memoization

> Security correction, 2026-07-03. Предыдущее решение с серверным `getSession()`
> отменено: Supabase не разрешает использовать данные из cookies без проверки как
> основание для авторизации.

**Проблема.** Layout и страница могут несколько раз запросить текущего пользователя и
профиль за один render. При этом оптимизация не должна заменять проверку подписи JWT
локальным чтением cookies.

### Функциональные требования

- FR-P2-1. `getCurrentUser()` и `getCurrentTutor()` обёрнуты в React `cache()`, поэтому
  layout и page одного render используют общий результат.
- FR-P2-2. `getCurrentUser()` на сервере вызывает `supabase.auth.getUser()`.
- FR-P2-3. Middleware сохраняет свой `getUser()` для refresh cookies и раннего redirect.
- FR-P2-4. Ошибка Auth или отсутствие пользователя приводят к redirect на `/login`.
- FR-P2-5. Отсутствующий профиль `tutor` является ошибкой целостности. Создавать
  профиль-fallback из `user_metadata` запрещено.

### Инварианты

- INV-P2-1. Данные непроверенной cookie-сессии не используются для решений о доступе.
- INV-P2-2. Запросы данных остаются ограничены RLS и `auth.uid()`.
- INV-P2-3. Один render выполняет не более одного page-level `getUser()` и одного
  `select tutor`, независимо от числа потребителей `getCurrentTutor()`.

### Критерии приёмки

- AC-P2-1. Unit-тест подтверждает вызов `getUser()` в server auth helper.
- AC-P2-2. Layout и page делят memoized user/profile result.
- AC-P2-3. Невалидная сессия редиректит на `/login`.
- AC-P2-4. Отсутствующий tutor profile завершает запрос ошибкой, без fallback.

Псевдокод: `02_dedupe-auth.md`.

## 4. P3 — выборка только активной вкладки + лимиты

**Проблема.** `students/[id]/page.tsx` грузит `listPackages` + `listPayments` +
`listLessonsByStudent` + `listHomeworksByStudent` **безусловно**, на любой вкладке — даже на
«Обзоре», где ничего из этого не показано. Все запросы — `select *` без `.limit()`; у тьютора
с многолетней историей это сотни строк уроков на каждый рендер, и каждая строка ещё прогоняется
через RLS (складывается с P4).

### Функциональные требования

- FR-P3-1. Баланс (`lessonsLeft`) показан на **всех** вкладках (карточка над табами) → лёгкий
  запрос баланса (`select lessons_left`) выполняется всегда; полный `listPackages` — только на
  вкладке «Пакеты».
- FR-P3-2. Данные грузятся **по активной вкладке** (матрица ниже), не все сразу.
- FR-P3-3. Списки-история ограничиваются `STUDENT_HISTORY_LIMIT` (новая константа, 50) и
  сортируются по убыванию; «ближайшие» (`scheduled`) — без лимита (их единицы), по возрастанию.
- FR-P3-4. Все затронутые запросы переходят с `select *` на явный список колонок (только нужные
  поля). Касается и `listStudents` на `/schedule` — там нужны лишь `id, name`.
- FR-P3-5. `currency`/профиль тьютора нужен только вкладке «Пакеты» (для `formatMoney`) →
  `getCurrentTutor()` вызывается лишь там (баланс-карточка денег не показывает).

#### Матрица загрузки по вкладке

| Вкладка    | Всегда           | Дополнительно                                                        |
| ---------- | ---------------- | -------------------------------------------------------------------- |
| `overview` | student, balance | —                                                                    |
| `packages` | student, balance | packages (полные), payments, tutor (currency)                        |
| `lessons`  | student, balance | upcoming (`scheduled`, asc), history (term., desc, limit)            |
| `homework` | student, balance | homework (limit), lesson-опции для привязки (`id, starts_at, topic`) |

### Инварианты

- INV-P3-1. Видимое содержимое каждой вкладки идентично текущему (для объёмов в пределах
  лимита). Лимит истории — продуктово допустимая усечка, как `SHARE_UPCOMING_LIMIT` для ссылки.
- INV-P3-2. Баланс считается из того же `packageBalance(...)` — формула неизменна.

### Краевые случаи

- EC-P3-1. История длиннее `STUDENT_HISTORY_LIMIT` → показываются последние 50; остальное —
  вне MVP (пагинацию «показать ещё» не делаем, фиксируем усечку в спеке).
- EC-P3-2. Вкладка «Домашка»: дропдаун привязки к уроку получает только лёгкие опции
  (`id, starts_at, topic`), не полные строки уроков.
- EC-P3-3. Неизвестный `?tab=` → дефолт `overview` (логика уже есть) → грузится минимум.
- EC-P3-4. Прямой переход по ссылке на вкладку (deep link) грузит ровно её данные.

### Критерии приёмки

- AC-P3-1. Открытие `?tab=overview` НЕ выполняет запросы payments/lessons/homework (проверка
  логами/Network); только student + balance.
- AC-P3-2. `?tab=lessons` грузит u pcoming + history (≤ лимита), не payments/homework.
- AC-P3-3. Ни один из затронутых запросов не использует `select *`.
- AC-P3-4. `/schedule` тянет учеников как `id, name`, не целиком.
- AC-P3-5. Регресс: все четыре вкладки отображают то же, что и до правки (ручной чек-лист).

Псевдокод: `03_tab-scoped-fetch.md`.

## 5. P4 — денормализация `tutor_id` + RLS без функции на строку

**Проблема.** Политики `package/payment/lesson/homework/lesson_series` используют
`using (public.owns_student(student_id))`. `owns_student` — функция, выполняющая `SELECT exists`;
в RLS с зависимостью от `student_id` Postgres вызывает её **на каждую возвращаемую строку**.
Выборка 200 уроков = 200 вызовов функции + 200 раз `auth.uid()`. Множится на конкурентных
юзеров. Особенно бьёт по `listLessonsInRange` (`/schedule`): диапазонный скан по `starts_at`
вынужден прогонять функцию на каждую строку всех уроков тьютора.

### Функциональные требования

- FR-P4-1. Новая миграция `0009_rls_tutor_id.sql` добавляет колонку `tutor_id uuid` в `package`,
  `payment`, `lesson`, `homework`, `lesson_series` (FK на `tutor`, `on delete cascade`).
- FR-P4-2. Бэкфилл `tutor_id` из родительского `student` для существующих строк **до** `set not null`.
- FR-P4-3. BEFORE INSERT триггер `set_tutor_id_from_student()` заполняет `tutor_id` из
  `student_id`, если он `null` → **код приложения не меняется** (вставляет только `student_id`).
- FR-P4-4. Политики переписываются с разделением по команде, чтобы горячий путь (SELECT) не
  вызывал функцию, а запись осталась корректной независимо от порядка триггеров:
  - `for select using (tutor_id = (select auth.uid()))`
  - `for update using (tutor_id = (select auth.uid())) with check (public.owns_student(student_id))`
  - `for delete using (tutor_id = (select auth.uid()))`
  - `for insert with check (public.owns_student(student_id))`
- FR-P4-5. `auth.uid()` всегда обёрнут в `(select auth.uid())` (InitPlan, одно вычисление на
  запрос) — и в новых политиках, и внутри `owns_student`.
- FR-P4-6. Индексы: `lesson(tutor_id, starts_at)` (под `/schedule`), `(tutor_id)` на остальных
  четырёх таблицах. Старые `*_student_id_idx` оставить (нужны для join/фильтров по ученику).

### Инварианты

- INV-P4-1. `tutor_id` дочерней строки всегда равен `tutor_id` её ученика. Гарантируется
  триггером на вставке; ученики не меняют тьютора в MVP → значение иммутабельно (не протухает).
- INV-P4-2. Видимость данных не меняется: тьютор видит ровно свои строки (тот же эффект, что
  `owns_student`, но без функции на строку).
- INV-P4-3. Запись чужому ученику невозможна: `with check (owns_student(student_id))` на
  insert/update — прежняя гарантия сохранена.
- INV-P4-4. Публичная ссылка (`getShareView`) ходит через service-role (RLS обходится по
  `share_token`) → правки политик её не задевают.

### Краевые случаи

- EC-P4-1. Вставка дочерней строки без `tutor_id` → триггер подставит из `student_id`.
- EC-P4-2. Бэкфилл должен пройти до `set not null`, иначе миграция упадёт на старых строках.
- EC-P4-3. `complete_lesson`/`reopen_lesson` делают UPDATE (не INSERT) `lesson`/`package` —
  `tutor_id` уже заполнен, триггер вставки не нужен; `with check` на update проходит по owns_student.
- EC-P4-4. Удаление ученика каскадит на детей (как раньше); FK `tutor_id` cascade — дублирующая
  страховка, конфликта нет.
- EC-P4-5. Применение на удалённый Supabase требует repair истории миграций перед push.

### Критерии приёмки

- AC-P4-1. `explain analyze` выборки уроков тьютора **не** содержит вызовов `owns_student`
  (функция ушла из горячего пути SELECT).
- AC-P4-2. `/schedule` (`listLessonsInRange`) использует индекс `(tutor_id, starts_at)`
  (index range scan, не seq scan + per-row функция).
- AC-P4-3. Тьютор видит только свои `lesson/homework/package/payment` (регресс RLS отсутствует).
- AC-P4-4. Вставка урока/ДЗ/пакета/платежа без явного `tutor_id` успешна и проставляет владельца.
- AC-P4-5. Попытка записи чужому ученику отклоняется RLS (`with check`).
- AC-P4-6. Миграция применена на удалённый Supabase; `lesson_series` и все 4 таблицы покрыты.

Псевдокод: `04_rls-tutor-id.md`.

## 7. Стратегия тестирования (TDD)

Раннер — **vitest** (`pnpm test`); стиль — юнит-тесты чистых функций (см. `recurrence.test.ts`,
`date.test.ts`). Запросы Supabase, RLS и storage напрямую не юнит-тестируются (нет DB/HTTP-
харнесса) → логику выносим в чистые хелперы, БД/сеть проверяем контрактом и ручным прогоном.

| Уровень           | Что                                                                                                      | Как                                      |
| ----------------- | -------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| Юнит (vitest)     | `collectHomeworkPaths`, `mergeSignedUrls` (P1); матрица «вкладка→набор запросов» как чистая функция (P3) | новые `*.test.ts`                        |
| Контракт сети     | 1 батч-запрос вместо 2N (P1); 0 лишних `getUser` (P2)                                                    | вкладка Network / счётчик запросов по AC |
| Контракт БД       | RLS-видимость и `with check`; `explain` без `owns_student` в SELECT (P4)                                 | ручной psql / pgTAP, сценарии AC-P4      |
| Сквозной (ручной) | регресс вкладок (P3), флоу ссылки ученика (P1), редирект разлогина (P2)                                  | чек-лист из критериев приёмки            |
| CI                | `pnpm typecheck && pnpm lint && pnpm test && pnpm build`                                                 | без `any`, зелёные                       |

Порядок: **P1 → P2 → P3 → P4**. P1/P2 — дешёвые и снимают самую тяжёлую сетевую нагрузку сразу;
P3 — среднее; P4 (миграция) — последней, с применением на удалённый Supabase и repair истории.
