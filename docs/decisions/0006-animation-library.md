# ADR-0006: Анимационная библиотека (Motion), правка «только Tailwind + shadcn»

- **Статус:** принято
- **Дата:** 2026-06-18
- **Решают:** владелец продукта, команда

## Контекст

`docs/DESIGN.md` §1 и правила проекта запрещали сторонние UI/визуальные библиотеки
(«только Tailwind + shadcn/ui»), а ADR-0001 закрепил стек и правило «менять без ADR
нельзя». Анимация до сих пор делалась только на CSS/Tailwind (`tailwindcss-animate`,
хелперы `revealUp`/`pressable` в `src/lib/styles.ts`).

Этого хватает для микровзаимодействий и появления «на загрузке», но не для движения,
которому нужен **детект вьюпорта или жесты**: появление секций по скроллу,
прерываемые/пружинные взаимодействия. Чисто на CSS это либо `IntersectionObserver`
вручную, либо scroll-driven CSS (частичная поддержка) — каждый раз новый кустарный
паттерн. Владелец продукта явно разрешил добавить библиотеку и поменять закон.

## Решение

- **Добавляем `motion`** (пакет `motion`, импорт из `motion/react`; преемник
  framer-motion) как **единственный** анимационный движок. React 19 / Next 15 — ок.
- **CSS — по умолчанию.** Hover/active, микровзаимодействия и появление на загрузке
  остаются на Tailwind/`tailwindcss-animate` (`revealUp`, `pressable`). CSS идёт вне
  основного потока и не зависит от JS.
- **Motion — точечно**, где CSS не покрывает: scroll-reveal (`whileInView`,
  `viewport={{ once: true }}`), жесты, пружины. Только в `"use client"`
  leaf-компонентах. Общий примитив лендинга — `src/features/landing/reveal.tsx`
  (`Reveal`, `useStaggerVariants`), обязателен `useReducedMotion()`.
- **Hero остаётся на CSS** (`revealUp`): появление на первом экране играет на загрузке,
  когда основной поток занят, — CSS тут надёжнее JS. Секции ниже сгиба — Motion.
- **Единая кривая** `cubic-bezier(0.23, 1, 0.32, 1)` и для CSS, и для Motion — один
  «голос движения».
- **GSAP** разрешён законом для сложной скролл-хореографии (pin/scrub), но в скоуп
  сейчас не берётся — для сдержанных reveal'ов это оверкилл.
- Правим правила проекта и `docs/DESIGN.md` §1/§11 — `motion` в списке явных исключений.

## Альтернативы

- **Только CSS scroll-driven анимации** (`animation-timeline: view()`). Без зависимостей
  и деградирует к «видно по умолчанию», но поддержка в браузерах неполная (Safari/FF),
  а API ещё незрелое для общего паттерна. Отклонено как основной механизм.
- **Кустарный `IntersectionObserver`-хелпер.** Ноль зависимостей, но это новый
  самописный примитив, который надо поддерживать; Motion даёт то же + жесты/пружины
  «из коробки» и идиоматичен для React. Отклонено.
- **GSAP + ScrollTrigger.** Мощнее для pin/scrub, но тяжелее и императивнее; не нужен
  для текущих задач. Разрешён законом, отложен до реальной потребности.
- **Оставить как было (только CSS).** Не давало чистого scroll-reveal — то, что
  владелец продукта и просил включить.

## Последствия

- (+) Чистый scroll-reveal и задел под жесты/пружины; единый примитив `reveal.tsx`
  переиспользуем за пределами лендинга.
- (+) Один «голос движения» (общая ease-out кривая для CSS и JS), reduced-motion
  учтён централизованно.
- (−) Лендинг-секции (features/steps/cta) стали `"use client"` и тянут ~небольшой
  JS-бандл Motion. Для маркетинговой страницы приемлемо; контент всё равно
  серверно-рендерится (текст в HTML), SEO-текст на месте.
- (−) **Тонкий риск**: у scroll-reveal начальное состояние `opacity: 0` инлайнится в
  SSR; без JS (отключён/часть краулеров/headless-скриншот без скролла) секции ниже
  сгиба могут остаться скрытыми визуально. Googlebot исполняет JS, текст в DOM есть,
  скринридеры читают DOM — поэтому риск косметический; при необходимости усилим.
- (−) Появилась библиотека, которую надо держать в актуальном состоянии.
- **Пересмотр:** если (а) понадобится сложная скролл-хореография — вводим GSAP
  отдельным решением; (б) SSR/no-JS-видимость станет критична — переводим reveal на
  CSS scroll-driven с деградацией «видно по умолчанию».
