# ADR-0005: Telegram-уведомления (репетитор + ученик)

- **Статус:** предложено
- **Дата:** 2026-06-17
- **Решают:** владелец продукта, команда

## Контекст

Сегодня единственный канал уведомлений — email через Resend (`src/lib/email/*`),
он отправляется **синхронно** в Server Actions при действии репетитора (выдача ДЗ,
создание урока). Email теряется, а аудитория продукта (СНГ/Грузия) живёт в Telegram.

Нужны два класса уведомлений: ученику — об уроках и ДЗ; репетитору — только важное
(заканчивается пакет, сдача ДЗ, подключение ученика). Часть из них — **отложенные**
(за сутки/2 часа до урока, приближение дедлайна ДЗ), а механизма доставки по
расписанию в проекте нет вовсе: нет крона, нет журнала уведомлений.

`docs/MVP.md` относит «Telegram-уведомления» к _Явно НЕ в этом билде_, поэтому решение
меняет ранее зафиксированный скоуп и оформляется ADR (правила проекта). Это сознательное
расширение: канал, который реально читают, плюс первый в проекте планировщик.

## Решение

- **Новый срез 11.** Фиче-зона `src/features/telegram` + канал-слой
  `src/lib/telegram/*` (зеркало `src/lib/email/*`: `client`/`send`/`messages`/`notify`,
  best-effort, мок-режим без токена).
- **Бот в webhook-режиме**, без SDK — тонкий слой на `fetch` к Bot API. Vercel
  serverless не держит long-polling. Webhook `/api/telegram/webhook` аутентифицируется
  заголовком `X-Telegram-Bot-Api-Secret-Token` (= `TELEGRAM_WEBHOOK_SECRET`).
- **Привязка.** Репетитор — по одноразовому коду `telegram_link_code` (TTL 15 мин):
  приложение чеканит код, бот ловит `/start t_<code>` и пишет `chat_id`. Ученик —
  по **тому же `share_token`, что в ссылке ученика** (`/start <share_token>`); это
  однозначно, т.к. `share_token` ⊂ `[a-z0-9-]` (см. `slugify`) и не содержит `_`.
  Подключить ученика может только владелец ссылки — отдельных кодов не плодим.
- **Две доставки.** Событийные (мгновенно, в Server Actions, рядом с email):
  ДЗ выдано/проверено, урок отменён/перенесён → ученику; ученик сдал ДЗ, мало
  занятий, ученик подключил Telegram → репетитору. Отложенные (по расписанию):
  урок за 24ч/2ч, дедлайн ДЗ → ученику.
- **Планировщик — внешний триггер.** `cron-job.org` / GitHub Actions дёргает
  защищённую `GET/POST /api/cron/notifications` (`CRON_SECRET`) каждые ~15 мин.
  Не зависит от плана Vercel; в духе «без очередей и воркеров» (MVP) — это всего лишь
  периодический опрос.
- **Идемпотентность.** Таблица `public.notification` с `UNIQUE(dedup_key)` (напр.
  `lesson_24h:<id>`). RLS включён **без политик** — таблица и `telegram_chat_id`
  доступны только доверенному серверному коду через service-role (webhook, cron,
  нотифаеры), как `admin_user` в ADR-0003.

## Альтернативы

- **Vercel Cron.** Один кодовый путь, но на плане Hobby крон только раз в сутки —
  напоминание «за 2 часа» нереализуемо без перехода на Pro. Отклонено (привязка к
  тарифу). Внешний триггер даёт нужную частоту на любом плане.
- **Supabase pg_cron + pg_net.** Не зависит от Vercel и частит, но добавляет
  расширения и HTTP-вызовы из БД — лишняя сложность для тонкого среза. Отложено как
  вариант, если внешний пингер окажется ненадёжным.
- **Telegram SDK (grammy/telegraf).** Удобный роутинг апдейтов, но нам нужны лишь
  `/start` и `/stop` + `sendMessage` — хватает `fetch`, без новой зависимости.
- **Polling-бот.** Требует постоянного процесса — несовместимо с serverless.
- **Отдельный код привязки ученика.** Лишняя сущность; `share_token` уже совместим с
  deep-link и совпадает с тем, что просили («тот же код, что в ссылке»).

## Последствия

- (+) Канал, который читают; первый планировщик в проекте — переиспользуем для
  будущих отложенных задач.
- (+) Слой 1-в-1 повторяет email: best-effort, мок без токена, та же идиома —
  низкий риск для существующих действий (уведомление не валит основную мутацию).
- (+) Поверхность PII мала: `chat_id` и журнал закрыты RLS; в логи уходит только
  числовой `chat_id`.
- (−) Внешний крон — ещё одна точка эксплуатации (нужно настроить пингер и секрет);
  при сбое пингера отложенные напоминания не уйдут.
- (−) Перенос урока после отправки 24ч-напоминания не сбрасывает dedup (повторно не
  напомнит) — частично компенсируется событием «урок перенесён».
- (−) Один `chat_id` на ученика (ученик ИЛИ родитель) и фиксированный часовой пояс
  рендера (`DEFAULT_NOTIFY_TZ`) — у репетитора нет поля TZ.
- **Пересмотр:** когда (а) понадобятся несколько подписчиков на ученика или
  персональный TZ; (б) внешний крон окажется ненадёжным — мигрировать на pg_cron;
  (в) появятся тумблеры по типам уведомлений (сейчас только подключён/отключён).
