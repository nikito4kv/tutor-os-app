# ADR-0003: Роль администратора (служебный аккаунт разработчиков)

- **Статус:** предложено
- **Дата:** 2026-06-14
- **Решают:** владелец продукта, команда

## Контекст

В tutorOS сегодня **одна роль**: каждый `auth.users` — это репетитор
(`public.tutor` 1:1, профиль создаётся триггером `handle_new_user`). Единственная
граница доступа — владение: `tutor_id = auth.uid()` и helper `owns_student`
(`supabase/migrations/0001_init.sql`, `0009_rls_tutor_id.sql`).

Кнопка «Поддержка» (`src/features/support`) **уже пишет** обращения в таблицу
`feedback` (`0006_feedback.sql`), но у таблицы только `INSERT`-политика и **нет
`SELECT`** — комментарий в миграции прямо говорит «reading/triage can be done from
the Supabase dashboard». То есть обращения собираются, но прочитать их внутри
приложения нельзя. Это и есть закрываемая дыра.

Команде нужен **внутренний служебный аккаунт** (надзор), а не продуктовая фича для
репетиторов: (1) инбокс обратной связи с триажем статуса; (2) дашборд с общими
цифрами (репетиторы/ученики/уроки), позже — деньги.

Это **не** roadmap-пункт «мини-школа / несколько преподавателей» (`docs/ROADMAP.md`
§6) — там продуктовые роли и общий пул учеников. Здесь ортогональная ops-роль.
`docs/MVP.md` относит «сложные роли» и «дашборды» к _не-в-этом-билде_, поэтому
решение меняет ранее зафиксированное и оформляется ADR (правила проекта).

## Решение

- **Механизм прав:** allowlist-таблица `public.admin_user(user_id)` + функция
  `public.is_admin()` (`SECURITY DEFINER`, без аргумента, по `auth.uid()`) —
  зеркало `owns_student`. RLS на `admin_user` включён **без политик** → таблица
  недостижима из `anon`/`authenticated`, читается только definer-функциями и
  service-role. Репетитор технически не может выдать права себе.
- **Админ — отдельная служебная роль**, не репетитор с флагом. После входа админ
  редиректится на `/admin`; своих учеников/уроков не ведёт.
- **Доступ к межтенантным данным минимальный:**
  - статистика — только **агрегаты** через gated `public.admin_stats()`
    (внутри `if not is_admin() then raise 'forbidden'`); админ **не** получает
    построчный `SELECT` на `student/lesson/payment`;
  - инбокс — построчное чтение `feedback` через RLS-политики
    `feedback_select_admin` / `feedback_update_admin` (это репорты репетиторов, не
    PII учеников). Service-role здесь не используется.
- **Автор обращения** в инбоксе показывается как оставленный пользователем
  `contact` + метка «зарегистрирован/аноним» (`tutor_id is not null`). Админ **не**
  читает таблицу `tutor` — email отправителя при необходимости смотрится в дашборде
  Supabase.
- **Маршруты:** новая группа `src/app/(admin)/` со своим лэйаутом-гейтом
  `assertAdmin()` и отдельным `AdminSidebar`. URL `/admin` (дашборд) и
  `/admin/feedback` (инбокс). Защита трёхслойная: middleware (auth) → `assertAdmin`
  (лэйаут) → БД (definer-гейт + RLS).

## Альтернативы

- **Колонка `is_admin` на `tutor`.** Самое простое по схеме, но текущая политика
  `tutor_update` — `using (id = auth.uid()) with check (id = auth.uid())` **без
  колоночной защиты**, поэтому репетитор смог бы выставить себе флаг
  (`update tutor set is_admin = true where id = auth.uid()`). Дыра эскалации;
  потребовала бы триггер/grant-защиту. Отклонено.
- **JWT `app_metadata.role = 'admin'`.** Сильнейшая изоляция (claim нельзя
  изменить из клиента, проверка в middleware без запроса к БД). Но добавляет работу
  с claim'ами, которой в проекте сейчас нет, и провижининг идёт через
  service-role/дашборд. Отложено как «более строгий» вариант на будущее.
- **Admin RLS `SELECT` на всех таблицах.** Дало бы дашборду читать строки напрямую,
  но открывает PII всех учеников (часто детей) админу. Не нужно: дашборду хватает
  счётчиков. Отклонено в пользу `admin_stats()` (только агрегаты).

## Последствия

- (+) Закрывает петлю обратной связи: обращения наконец читаются и триажатся в
  приложении.
- (+) Минимальная поверхность PII: счётчики, а не строки; инбокс показывает только
  `contact`, не email репетитора.
- (+) Чистый RLS + `SECURITY DEFINER`, без нового использования service-role —
  меньше радиус поражения; всё в идиоме проекта (`owns_student`).
- (−) Провижининг админа — ручной SQL (`insert into admin_user …`), UI управления
  нет (осознанно тонко).
- (−) Инбокс пока не резолвит email/имя отправителя (нужен был бы доступ к `tutor`).
- (−) Скоуп выходит за тонкий MVP репетитора — оправдано как ops-инструмент.
- **Пересмотр:** когда понадобятся (а) денежные цифры на дашборде — добавляется
  ключ в `admin_stats()`; (б) продуктовые роли «мини-школы» — пересмотреть, не
  обобщается ли `admin_user` во что-то большее (скорее нет: это разные сущности).
